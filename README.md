# Casino v2 — Autonomous LLM Agents with Dialogue Economy

## Overview

Five autonomous LLM agents play European roulette **and** trade with each other.
Each agent can:
- Place casino bets using their personal strategy
- **Sell strategies** to other players for coins
- **Offer loans with interest**
- **Buy tips / information** from others
- **Form alliances** or act as information brokers

All state is stored in `table/` as JSON files. All events are logged to `logs/`.

## Architecture

```
common.py          — roulette rules & payouts (unchanged from v1)
llm_client.py      — LLM API client (Ollama / Jan / OpenAI-compatible)
agent_v2.py        — PlayerAgent: abstract prompt, betting synapse, dialogue synapse
croupier_v2.py     — spins wheel, distributes results
game_logger.py     — writes logs/full_game.txt and logs/player_<id>.txt
run_game_v2.py     — orchestrator (4 phases per round)
config_v2.ini      — configuration
```

## Per-Round Flow

```
Phase 0: Apply last round's casino results + update betting synapse
Phase 1: Dialogue phase — agents negotiate, sell, transfer money
Phase 2: Place bets
Phase 3: Croupier spins, results written
```

## Player State Files (in table/)

| File | Contents |
|------|----------|
| `balance_<id>.json` | Current balance |
| `notes_<id>.json` | **Betting synapse** — casino strategy (LLM-written, auto-updated) |
| `dsyn_<id>.json` | **Dialogue synapse** — memory of deals with other players |
| `prompt_<id>.txt` | **Abstract system prompt** — player's role/persona (LLM can rewrite it) |
| `history_<id>.json` | Full round history |
| `dlg_r<NNN>_<a>_<b>.json` | Saved dialogue between players A and B in round N |

## Dialogue Rules

- Each player may speak to **at most 2 other players** per round
- Each dialogue has **at most 4 message exchanges**
- Either party can **transfer coins** mid-dialogue (payment for service, loan, etc.)
- After each dialogue both players update their **dialogue synapse**
- Next round: player reviews synapse before deciding to talk again

## Log Files (in logs/)

| File | Contents |
|------|----------|
| `full_game.txt` | Complete event log — every action, dialogue turn, balance change |
| `player_<id>.txt` | Events filtered to that player + their dialogues |

## Running

```bash
# Edit config_v2.ini to point to your LLM server

# Run 10 rounds
python3 run_game_v2.py --config config_v2.ini --rounds 10

# Force a specific winning number in round 1 (testing)
python3 run_game_v2.py --rounds 5 --winning-number 17
```

## Abstract Prompt

Each player starts with the same `DEFAULT_ABSTRACT_PROMPT` (in `agent_v2.py`).
After each round, the agent can **rewrite its own system prompt** — changing its
persona from, say, a "conservative gambler" to an "information broker charging 2
coins per tip". The new prompt is saved to `table/prompt_<id>.txt`.

## Example Dialogue (what agents actually say)

```
[player1]: Hi player2. I've noticed you've been winning. Would you share your
           strategy for 3 coins?
[player2]: Make it 5 and I'll tell you: always bet even_money red, small amounts. [+5 coins]
[player1]: Deal. [transfers 5 coins to player2]
[player2]: Thanks. And if it doesn't work, come back — I'll refund 2 coins.
[player1]: See you next round for feedback, charging 1 coin.
```

## Extending

- Add more players in `[game] players = player1,...,player8`
- Change `max_bet_fraction` to control how aggressive bets are
- Add a human player: use the original `player.py` against the same `table/`
- Analyse `logs/full_game.txt` for emergent economic behaviour

### Чек-лист (FIX-19)

Файл `checklist_<pid>.md` **принадлежит агенту**. Стартовые заголовки
(`Agenda this round`, `Owed TO me`, `I owe / I promised`, `Verify before
paying`, `Notes`) — только подсказка: ни один не обязателен, ничего из файла
не парсится кодом, и агенту прямым текстом сказано, что он вправе выбросить
структуру целиком и хранить что угодно в любом виде. На это есть тест
`test_agent_may_discard_the_suggested_structure_entirely`.

Два шага работы с ним:

| шаг | когда | что видит |
|---|---|---|
| `plan_round` | перед диалогами игрока | чек-лист, скорборд, свежие строки журнала, своя история раундов, репутационная карта, номер раунда |
| `update_checklist` | после **каждого** диалога, у **обеих** сторон | чек-лист и полный транскрипт только что закончившегося разговора |

Показывается он в трёх точках принятия решений: выбор собеседника, каждая
реплика диалога, выбор ставки.

`update_checklist` намеренно отделён от `update_dsyn`: та пишет долгосрочную
репутацию («можно ли ему верить»), эта — что конкретно теперь надо сделать
(«обязался вернуть 24 к концу r5 — стребовать»).

**Цена.** +1 вызов на игрока за раунд и +2 на каждый диалог: примерно **+20%**
к длительности партии и +6 п.п. контекста (71% вместо 65%). Отключается
`[game] use_checklist = false` — при этом он не только перестаёт обновляться,
но и **исчезает из промптов**, иначе выключение экономило бы вызовы, но не
контекст. Обновление после каждого диалога можно отключить отдельно:
`checklist_after_each_dialogue = false` — тогда чек-лист правится только на
планировании.

Потолок `[memory] checklist_chars` обязателен по уроку FIX-12: любой
самопишущийся файл без ограничения растёт, а Ollama режет промпт с начала.

### Целостность данных (FIX-16, FIX-17)

Оба фикса про одно: **факты в журнале должны оставаться фактами**, иначе
проверяемость из FIX-13/14 не стоит ничего.

Журнал теперь идемпотентен — одна запись на пару `(игрок, раунд)`,
переигрывание раунда замещает старую запись и пересортировывает журнал по
раундам. То же для личной истории.

Выключатель считает подряд упавшие вызовы и после `[api] max_consecutive_failures`
бросает `LLMUnavailable`. Это исключение агенты **не гасят** (в отличие от
обычных ошибок, которые уходят в заглушку — именно поэтому падение сервера и
осталось незамеченным): раунд обрывается, `save_last_round` не вызывается,
процесс выходит с кодом 2. Благодаря чекпойнтам Фазы 0 и фазы диалогов раунд
доигрывается после починки сервера без потерь.

Битый JSON выключатель **не** взводит: он означает, что сервер жив и отвечает,
просто модель не попала в формат. Иначе выключатель срабатывал бы на здоровом
сервере.

Состояние выключателя вынесено в отдельный `_Breaker`, а не в атрибуты
`LLMClient`: это здоровье сервера, а не свойство класса-обёртки. Хранение в
классе оказалось хрупким дважды — `cls._failures += 1` из подкласса молча
заводит отдельный счётчик на подклассе, а обращение по глобальному имени
внутри собственных методов ломается при подмене имени в модуле.

### Проверяемость и скорборд (FIX-13, FIX-14)

Ни то, ни другое не запрещает врать — в этом вся игра. Меняется только то,
что враньё становится **опровержимым**.

`CORE_SYSTEM_PROMPT` теперь фиксирует: колесо европейское (37 секторов, 0–36,
никакого 00), спин ровно один за раунд и крутит его крупье, «тестовых сессий»
и «прогонов» не существует, а каждая ставка каждого игрока попадает в публичный
журнал. Отсюда два следствия, и они названы явно: чужие заявления о **уже
случившемся** надо сверять с журналом, а свои — сверят с ним же. Торговля
прогнозами и стратегиями при этом остаётся законной: они не проверяемы
по определению, и в этом нет обмана.

Скорборд отдаёт готовый агрегат вместо арифметики:

```
[Casino scoreboard — VERIFIED totals from the public ledger]
  player3: casino P&L=+20c over 1 bet(s) (staked 20, returned 40, won 1/1),
           mostly even_money, last bet in r1
```

Против заявления «12 спинов, dozen и split, 50% попаданий» этого достаточно.
Скорборд подставляется в три точки: выбор собеседника, **сам диалог** и выбор
ставки. Новой информации он не добавляет — журнал и так публичен, — убирается
только арифметический барьер. Баланс намеренно не включён: он содержит итог
приватных сделок, и его публикация выдала бы третьим лицам исход чужих
диалогов.

Окна сырого журнала при этом **уменьшены** (50/80 → 30/40): агрегат по партии
теперь несёт скорборд, а сырые строки нужны лишь для точечной сверки
конкретного заявления. Пик контекста — 65%, и он не растёт с длиной партии.

### Персона (FIX-12)

Замер роста персоны при `num_ctx=8192` (остальное — под порогами `[memory]`):

| персона | было | стало |
|---|---|---|
| 1200 симв | 66% | 66% |
| 6000 | 81% | 78% |
| 10000 | 98% | 78% |
| 15000 | **129% — обрезка** | 78% |
| 50000 | — | 78% |
| 200000 | — | 78% |

Три уровня защиты, потому что одного мало:

1. **Объявленный лимит** — в промпте рефлексии сказано `MAX N characters` и объяснено, почему (персона добавляется к каждому запросу).
2. **Обрезка при записи** — модель регулярно превышает объявленный лимит, поэтому на слово не верим: `_truncate_text` режет по границе предложения.
3. **Жёсткий потолок в `abstract_prompt`** (`persona_chars × 2`) — без вызова LLM, работает даже до первой рефлексии и при правке `prompt_<id>.txt` руками.

Плюс сжатие через LLM при превышении порога — с двумя тонкостями, каждая из
которых обнаружилась замером:

- `system` при сжатии — это `CORE_SYSTEM_PROMPT`, **не** `abstract_prompt`.
  Последний содержит саму персону, и раздутая персона уехала бы в запрос дважды.
- Персона жёстко режется **до** отправки на сжатие. Иначе вызов кладёт её в
  user-сообщение целиком: на 50k символов это давало 166% контекста, то есть
  вызов, призванный вылечить переполнение, переполнял сильнее всего остального.

### Ротация порядка хода (FIX-10)

```
раунд 1: p1 p2 p3 p4 p5      раунд 4: p4 p5 p1 p2 p3
раунд 2: p2 p3 p4 p5 p1      раунд 5: p5 p1 p2 p3 p4
раунд 3: p3 p4 p5 p1 p2      раунд 6: p1 p2 p3 p4 p5   (цикл повторяется)
```

За цикл из N раундов каждый игрок ровно по одному разу занимает **каждую**
позицию — и слепую первую, и всезнающую последнюю. Ротация детерминирована и
зависит только от `round_no`, поэтому порядок пересчитывается один в один при
восстановлении после Ctrl+C (в `dialogue_phase_state.json` лежит индекс именно
в этом, повёрнутом порядке). Фактический порядок каждого раунда пишется в лог:

```
[GAME] Dialogue order for round 4: player4 → player5 → player1 → player2 → player3
```

Порядок Фаз 0 и 2 не ротируется намеренно: там он ни на что не влияет — все
ставки раунда разыгрывает один-единственный спин, а начисления не зависят от
последовательности.

### Что осталось НЕ закрытым: обязательства между раундами

FIX-9/9b снижают частоту «договорились и разошлись в ноль», но **не устраняют
причину**. В игре нет объекта обязательства: обещание «заплачу в следующем
раунде» живёт только свободным текстом в `future_intent` и `deals_done`, и никто
не проверяет, было ли оно исполнено. Для системы обещание и его исполнение
неразличимы, поэтому `trust_score` строится на впечатлении LLM, а не на факте.

Полное решение — структурированный реестр долгов (`promise` со схемой
`{to, amount, due_round}`, сохраняемый вне синапсы, автоматически сверяемый в
начале следующего раунда и подставляемый обеим сторонам как проверенный факт).
Это меняет формат состояния, поэтому в один заход с денежными фиксами не вносил.

### Проверка сохранения денег

`TestMoneyConservation` сверяет сквозной инвариант после каждой игры:

```
сумма балансов == старт × игроков − все ставки + все выплаты
```

Казино — единственный источник и сток монет; переводы между игроками их не
создают и не уничтожают. Двойного подсчёта в связке
«списание в Фазе 2 → `payout = amount + amount × odds` в `evaluate_bet`»
нет — инвариант сходится ровно.

### Контракт с моделью перевёрнут

Было: «верни ВЕСЬ список» — и любая забывчивость стирала реестр.
Стало: модели **показывают** текущий список с `id` и просят вернуть **только
новое и изменившееся**; всё неупомянутое сохраняется само.

```
Your tracked promises (reference them by id when updating):
  id=1: player2 owes you 24c, due r5, status=open — "loan"
```

> ONLY the commitments that are NEW or that CHANGED just now. Anything already
> in your tracked list that you do not mention stays exactly as it is — you do
> NOT need to repeat it, and leaving it out does not delete it.

Отказ модели теперь означает «ничего не изменилось» вместо «удалить всё»:
безопасность по построению, а не по добросовестности 8B-модели.

Опознание записи — сначала по `id`, затем по отпечатку
`(направление, контрагент, сумма, срок)`: модель часто не возвращает `id`, и
без отпечатка то же обещание плодило бы дубли на каждом ходу.
